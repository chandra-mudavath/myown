Data Models / Final-Data-Model.md · revision 2

UrTax schema map

Revision 2 of the data model, checked against the tables that already exist in app/models/. Option lists such as roles, document types and tax years are now lookup tables, so adding one is a single row. Every account kind shares one profile table. Staff, staff profile and documents are filled in from the real code.

Every table and column here matches Data Models/schema.sql in the repo. Ids are UUIDs generated by the app, except on lookup tables, which use small fixed integers. Every record the UI shows also has its own unique readable number, such as CLI-00000001, FLI_0000001 or DOC-0000001. URLs keep using the UUID.

Your three points

1. New roles, document types and tax years

staff_roles, document_types and tax_years share one lookup shape: code, name, sort_order, is_active. Adding an option is one row from an admin settings screen. The same pattern now covers tax_types and case_stages, which replace free-text columns.

2. New account kinds beside client, staff, admin and HR

The AccountType enum becomes an account_types table that holds each kind's number prefix and portal path. Name, phone, picture and address move to one shared user_profiles table. Every "who did it" column becomes a real *_account_id foreign key, so a new kind is one row.

3. Staff schema, staff profile and documents

Filled in from the real code. staff keeps job_title and notifications_seen_at, and its profile is in user_profiles. Case documents reuse filing_documents and document_comments. HR staff documents reuse the same document_types catalog.

Reused instead of replaced: the tax case is the existing tax_filings table, which keeps all its intake fields. document_comments replaces revision 1's document_reviews. Revision 1's filings is renamed irs_submissions so it can't be confused with tax_filings. HR moves out of StaffRole and becomes an account type.

Overview

relationships only

Each account has one profile and one kind-specific record. A client opens tax cases, and documents, IRS submissions and invoices attach to each case. Every "done by" column points back to auth_accounts.

Messaging

newchat_threads, chat_participants, chat_messages, chat_attachments, chat_query_topics

Every conversation is one chat_threads row. kind is DIRECT (two internal members), GROUP (named internal group), CASE (client and case team, one per filing) or QUERY (a client question). case_id is set only when the conversation is about a filing. Clients never join DIRECT or GROUP threads; account_types.is_internal decides who may. Nothing is deleted: a daily job sets hidden_at 3 months after the case completes, the query is resolved, or (general chats) the last message, and hidden threads stay for audit.

Adding a new kind of account

example: Auditor
  1. Insert a row into account_types: AUDITOR, prefix AUD, portal /auditor.
  2. Sign-up writes auth_accounts and user_profiles. Name, phone, picture and address need no new table.
  3. Only if auditors have fields of their own, add a small auditors table keyed by account_id.
  4. Uploads, comments, notifications and the audit log already work, because they all point at auth_accounts.id.
  5. Code still needed: the portal's routes and pages, and a require_account_type("AUDITOR") guard in app/core/deps.py.

Later: if a new role or account kind should get different powers without code changes, add permissions and link it to account_types and staff_roles. That is phase 2 and not part of this revision.
